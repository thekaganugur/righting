# `righting` v1 design

**Status:** agreed for dogfooding

## Purpose

`righting` is an agent-first, local architecture-policy tool inspired by Juval Löwy's *Righting Software*. It helps a project declare and mechanically enforce volatility-based dependency boundaries.

It is for the author's projects first and may be published as an open-source `0.x` npm package. Documentation credits *Righting Software* but uses original wording.

## Product boundary

```text
righting.json
  ↓
righting core
  ↓
righting + ESLint adapter (v1)
```

- **`righting` core** owns the policy schema, `volatility@1` preset, agent documentation, policy validation, and baseline-ratchet semantics.
- **`righting + ESLint adapter`** translates the policy to existing ESLint checks and uses ESLint's native suppression storage.
- Future adapters may target Oxlint, RuboCop, and other ecosystems. They are not part of v1.
- The core is TypeScript/Node, runs locally, and has no telemetry or hosted service.
- `righting` is generic; ESLint is only the first enforcement adapter.

## Policy model

`righting.json` is a versioned, schema-validated, language-neutral policy file. The initial preset is pinned as `volatility@1`.

The preset models the six canonical roles:

- Client
- Manager
- Engine
- ResourceAccess
- Resource
- Utility

Projects use **aliases**, not custom roles. For example, `page` and `component` may both map to Client; `repository` may map to ResourceAccess. An alias changes local vocabulary and path matching, never the canonical role's behavior.

A policy contains explicit path/package mappings. Ambiguous role or scope matches are configuration errors. Ordinary external dependencies are allowed unless explicitly marked as protected Resource or Utility dependencies. An unresolved local import is an error, not an allowed bypass.

### Default structural graph

The default is as close to the book's closed architecture as static source evidence permits:

```text
Client → Manager
Manager → Engine / ResourceAccess
Engine → ResourceAccess
ResourceAccess → Resource
all roles → Utility
```

Resources and Utilities must not reach into business roles. Direct Manager → Manager source imports are forbidden; the book's queued Manager interaction is documented as only partially checkable by static adapters.

Every stable semantic policy rule has a `righting` policy-rule key. Adapters may use different native lint rule IDs but map findings back to the same policy key.

### Deliberate variations

The policy remains strict by default. It supports:

- named opt-ins: `clientReadsAccess`, `pureEngines`, and `contextFirewall`;
- global, reason-required edge overrides among canonical roles.

Loosening is a last resort. The preferred order is to fit the design into the default policy, clarify/extract the design, then tighten where appropriate, and only then loosen with a documented reason.

There is no v1 per-file/per-line `righting` waiver framework. The only exceptions are policy-wide variations and grandfathered legacy debt.

## Scope and contexts

Role and scope are separate concepts.

When `contextFirewall` is enabled, a project explicitly configures:

- **context** paths, carrying a captured business-context identity;
- **shared** paths; and
- unscoped paths.

The generic scope rules are:

- one context cannot import another context;
- shared code cannot import a context;
- contextual code may use shared code when the role graph permits it;
- contextual Clients may compose shared Clients and Clients in the same context.

This supports page/component, controller/view, or other Client composition without hard-coding framework names. Helpers are local only when a context makes “local” mechanically meaningful; `righting` does not invent a seventh support-file role.

V1 lets unscoped application/router code wire context entry points. A declared composition-root scope is deferred until dogfooding proves it necessary. Nested scopes, public cross-context APIs, and arbitrary scope graphs are also deferred.

## Enforcement scope and adapter capabilities

V1 checks static source dependencies, including imports, exports/re-exports, `require`, and dynamic imports. Type-only imports count as architectural dependencies.

It does **not** claim to prove runtime behavior. For example, it cannot prove that an allowed Manager interaction was truly queued.

Generated guidance labels rules as:

- **lint-enforced**;
- **partially checked**; or
- **guidance only**.

The full qualitative design judgment in the book—contract quality, Manager/Engine ratios, identifying real volatility, and use-case validation—is not lint-enforced.

`righting + ESLint adapter`:

- requires an existing modern ESLint flat-config setup;
- must preserve existing lint scripts and typed-lint settings;
- does not require or add type-aware analysis for Righting's static rules;
- uses existing ESLint plugins for path/import enforcement rather than inventing an import graph engine;
- covers re-export and other dependency-node forms, so no second graph tool is included in v1 solely for barrel laundering;
- uses namespaced composed rule entries in the project's existing `eslint-suppressions.json`.

Legacy ESLint configurations and repositories without ESLint are reported as unsupported by this adapter; the integration process does not migrate or install a linter for a project.

Every future adapter must pass common allowed/forbidden dependency fixtures before it is called supported. Adapters declare their enforcement capabilities and limitations explicitly.

## Strict, agent-guided integration

`righting init` is non-interactive by default and machine-readable where useful. It is safe to re-run.

It does not infer a repository's architecture or rewrite an ESLint config. Instead, it creates an explicitly incomplete policy template. Lint activation remains blocked until an agent and its user/developer complete and approve the needed architectural decisions.

Strict setup means no silent permissive fallback. It does **not** mean requiring fake configuration for concepts that genuinely do not apply.

The v1 CLI is limited to:

- `init`
- `baseline`
- `docs`

`init` updates a marked, managed block in root `AGENTS.md` while preserving project-owned content. `init --skills` is an explicit opt-in that creates relative symlinks to packaged Righting skills under `.agents/skills`, the cross-agent discovery convention; it never replaces a project-owned skill with the same name. Default setup remains fully usable without an agent skill; skills are optional accelerators.

## Agent support

All skills follow the Agent Skills standard and avoid harness-specific assumptions. The optional `.agents/skills` links make the packaged skills discoverable to compatible agents without copying stale skill content.

### Integration skills

- **`righting-integrate`** handles policy decisions, aliases, scopes, agent/user approval, docs, and baseline intent.
- **`righting-eslint`** handles ESLint flat-config wiring, resolver setup, native suppression workflow, and verification.

The ESLint integration protocol is fixed: inspect the existing config, preserve its settings, add only the adapter configuration, run the existing lint command, report typed-lint presence and outcome, and never restructure lint commands without approval.

### Generated project guidance

The `AGENTS.md` block explains the local aliases, enforced boundaries, adapter limitations, and available design-review skill. It may render optional, schema-controlled extras:

```json
{
  "extras": {
    "domainVocabulary": "CONTEXT.md",
    "goldenExamples": {
      "page": "src/orders/orders.page.tsx",
      "manager": "src/orders/orders.manager.ts"
    }
  }
}
```

Extras are agent guidance only. `righting` validates configured paths exist, but does not parse domain documents or judge whether a golden example is architecturally good.

### `righting-design-review`

This opt-in advisory skill ships in v1 and improves through dogfooding. It:

- reviews a stated behavior/change goal and focused diff or files;
- inspects the policy and relevant code before asking questions;
- uses configured domain vocabulary and golden examples when available;
- asks design questions one at a time;
- reports evidence, open questions, and risks—not scores or pass/fail verdicts;
- surfaces adapter limitations;
- conservatively suggests policy changes only when the default cannot express a justified design;
- never changes policy, CI, or project files automatically.

It returns its record in chat unless explicitly asked to write a Markdown artifact. It uses an original checklist inspired by *Righting Software*, not reproduced book text.

## Legacy debt and ratchet

The adapter owns native baseline-file mechanics; `righting` owns the policy that baseline debt may only shrink.

For ESLint:

- native entries live in the project's shared `eslint-suppressions.json`;
- `righting + ESLint adapter` namespaces its entries and normalizes them for the core;
- the core performs the Git-base comparison;
- CI supplies the base ref explicitly;
- v1 compares per-file/per-rule counts.

The ESLint count ratchet is transparent but not exact: it catches increases but cannot distinguish a same-count swap within the same file/rule pair.

A baseline may never grow during normal work. A deliberately enabled/expanded policy may establish an initial legacy baseline only with an explicit migration reason. Git is required for baseline/ratchet features, not for ordinary boundary linting.

## V1 non-goals

- architecture inference or automatic role assignment;
- code skeleton generation;
- generic AST/code-pattern rules (for example, mutation or raw-state-string checks);
- runtime/queue verification;
- visual dashboards;
- framework templates;
- a public adapter SDK;
- a custom per-violation waiver framework;
- cycle detection as a `righting` responsibility;
- automatic lint-config migration or setup suggestions that claim architectural certainty.

## Dogfood acceptance

Before public release, an agent must successfully use `righting` in a real TypeScript repository to:

1. integrate it non-interactively with user-approved architecture decisions;
2. configure a managed area and policy aliases/scopes;
3. establish committed legacy debt where needed;
4. receive generated guidance;
5. make a normal feature change, encounter an actionable boundary failure in the normal lint loop, and repair it using the policy/golden example; and
6. leave CI green without a human architecture intervention.

Dogfooding is also how `righting-design-review`, adapter performance, future composition-root scopes, stronger baseline identity, and future adapters will be refined.
