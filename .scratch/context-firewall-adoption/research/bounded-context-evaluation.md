# Research: optional `contextFirewall` adoption

## Summary

`contextFirewall` should be **omitted for this repository now**. The repository explicitly identifies itself as single-context (`AGENTS.md`; `docs/agents/domain.md`), its root `CONTEXT.md` contains one shared product vocabulary, and the reviewed product/design evidence contains no independently meaningful domain models, context map, separate ubiquitous languages, or autonomous ownership boundaries. A static firewall is useful only after maintainers have approved real context identities and relationships; `righting-integrate` should recognize decisive existing evidence, refer ambiguous design work to a bounded-context specialist, and never derive contexts from directories.

## Repository findings

1. **High — no evidence supports proposing `contextFirewall` here.** `AGENTS.md` says “This is a single-context repository”; `docs/agents/domain.md` defines a multi-context repository by an explicit root `CONTEXT-MAP.md` and per-context `CONTEXT.md` files, while the actual root `CONTEXT.md` presents one Righting vocabulary. No reviewed source establishes distinct domain models or context relationships. Therefore the current disposition is **omit**, not “invent scopes and see whether inspection passes.” Paths: `AGENTS.md`, `docs/agents/domain.md`, `CONTEXT.md`.
2. **High — the integration instructions need a bounded, non-inferential decision rule.** `skills/righting-integrate/SKILL.md` requires an evidence-backed `propose` or `omit` for every variation, but gives no `contextFirewall` evidence threshold or specialist referral state. `docs/policy-language.md` explains mechanics and required `scopes`, not how context identity is established. This creates a failure mode in which folder names can be mistaken for maintainer policy. Paths: `skills/righting-integrate/SKILL.md`, `docs/policy-language.md`.
3. **Medium — repository records already acknowledge the observed failure mode.** The dogfood record says one of five adoption runs proposed `contextFirewall` spuriously for a single-context app, and claims docs were fixed to say the variation is for independently owned bounded contexts; that criterion is not present in the reviewed current `docs/policy-language.md`. Paths: `.scratch/righting-integrate-dogfood/PRD.md`, `docs/policy-language.md`.
4. **No capability mismatch, provided adoption is explicit.** The product boundary is intentionally static: `docs/capabilities.md` says the firewall establishes only cross-context and shared-to-context source-import restrictions, not runtime behavior; `design/2026-07-18-righting-v1.md` says scope and role are separate and that Righting does not infer architecture. Paths: `docs/capabilities.md`, `design/2026-07-18-righting-v1.md`.

## External findings

1. **A bounded context is a model boundary, not a directory label.** Eric Evans defines it as the boundary—typically a subsystem or a team’s work—within which a particular model is defined and applicable. He calls for boundaries to be explicit in team organization, application usage, and physical manifestations such as code and schemas. Physical layout is therefore corroborating implementation evidence, not sufficient domain evidence by itself. [DDD Reference, pp. vi, 2](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)
2. **Positive evidence is semantic and organizational.** Strong indicators are distinct models for the same concept, vocabulary changing across groups, different user communities/jobs, independently working teams, and explicit relationships between those models. Fowler describes bounded contexts as internally unified models whose boundary commonly follows a language/culture change; Microsoft likewise recommends first mapping business functions with domain experts and stakeholders, then grouping functions that share a domain model and documenting interactions in a context map. [Fowler: Bounded Context](https://martinfowler.com/bliki/BoundedContext.html) [Microsoft: Domain analysis](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis)
3. **A static import firewall preserves an approved boundary continuously.** Evans warns that combining code based on distinct models makes software unreliable and difficult to understand. First-party ArchUnit guidance explains the mechanical benefit: architecture dependency rules can run automatically in CI rather than relying on periodic human review, exposing drift as the system and team evolve. For Righting, that benefit is narrower: prevention of direct static context-to-context and shared-to-context imports; it says nothing about runtime calls or model quality. [DDD Reference, p. 2](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [ArchUnit: Why test your architecture?](https://www.archunit.org/motivation)
4. **Premature boundaries impose refactoring and false-constraint costs.** Fowler reports that stable boundaries are difficult even for experienced architects to identify initially and that moving functionality across prematurely separated services is harder. Evans also warns that splitting into ever-smaller contexts loses useful integration and coherence. Microsoft recommends iterative boundary evaluation, starting coarse when uncertain, and explicitly says there is no mechanical process for finding the correct design. [Fowler: Monolith First](https://martinfowler.com/bliki/MonolithFirst.html) [DDD Reference, p. 5](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf) [Microsoft: Domain analysis](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis) [Microsoft: Identify microservice boundaries](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/microservice-boundaries)
5. **Folder-first declaration can encode technical or accidental structure as policy.** Microsoft directs teams to design around business capabilities rather than horizontal technical layers, to perform domain analysis before choosing implementation details, and to revisit boundaries when ownership or coordination does not fit. A folder name alone cannot show a distinct model, language, ownership boundary, or approved relationship. [Microsoft: Domain analysis](https://learn.microsoft.com/en-us/azure/architecture/microservices/model/domain-analysis)

## Minimal decision aid for `righting-integrate`

The skill should evaluate this variation without requiring contexts, inferring policy, or conducting a DDD interview:

| Disposition | Evidence test | Integration action |
|---|---|---|
| **omit** | Project calls itself single-context; or only folders/package names suggest contexts; or there is no maintainer-approved evidence of at least two independently meaningful model/language boundaries. | Record `contextFirewall: omit` with the concrete evidence/absence. Do not create `scopes`, ask a DDD questionnaire, or treat omission as incomplete adoption. **Current repository result.** |
| **consider with specialist** | Evidence conflicts or is design-judgment-heavy: overloaded domain terms without declared boundaries; multiple teams or candidate models but no approved context identities/map; frequent legitimate cross-boundary collaboration; unclear `shared` ownership; or proposed scope paths overlap/leave uncertain wiring. | Stop variation design and refer the bounded-context question to a design specialist. Give the specialist the observed terms, ownership/model evidence, candidate interactions, and paths; do not propose scope policy. Resume only from maintainer-approved context identities and relationships. |
| **propose for approval** | Existing project-owned artifacts already name at least two contexts and independently explain their models/languages or ownership, plus their allowed integration relationships; source paths can implement those approved identities unambiguously, including explicit `shared` and `unscoped` areas. | Produce exact `contextFirewall` plus `scopes` in the approval packet, enumerate current matches and forbidden/unresolved crossings, state static/runtime limits, and request exact maintainer approval. Existing boundaries justify the proposal; directory shape merely maps them. |

**Referral triggers, not interview questions:** contradictory domain vocabulary across areas; disagreement over whether two areas share one model; boundaries based only on repository topology; unclear ownership of shared code; need for a legitimate cross-context source API not expressible by the v1 firewall; ambiguous/overlapping scope paths; or evidence that enforcement would force unnatural moves/duplication. These require bounded-context design judgment because Righting’s own capability catalog classifies model quality and real design judgment as guidance-only (`docs/capabilities.md`).

## Gaps and residual risks

- No specialist domain analysis was performed, intentionally. If maintainers believe this repository contains multiple business models despite its explicit single-context documentation, that contradiction is a **specialist referral**, not an integration inference.
- Static enforcement cannot detect runtime calls, data coupling, duplicated concepts, or bad context definitions. An approved but incorrect scope map can make the firewall actively harmful by blessing accidental boundaries or forcing circumvention.
- The proposed “propose” threshold is intentionally conservative. A project may have valid bounded contexts without formal documents, but eliciting and approving those is specialist design work outside `righting-integrate`.
