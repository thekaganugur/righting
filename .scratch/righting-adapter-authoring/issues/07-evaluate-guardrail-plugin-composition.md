# Evaluate established guardrail-plugin composition

Type: research
Labels: wayfinder:research
Status: resolved
Blocked by:

## Question

Which validated project-local adapter mechanics should the generic authoring path obtain by composing established native or ESLint-compatible guardrail plugins—especially `eslint-plugin-boundaries` and, where relevant, file-naming plugins—and which mechanics must remain in a thin Righting mapping layer? Test the recommendation against normalized-contract consumption, Oxlint compatibility, all `role-dependency` conformance scenarios, stable Righting policy-rule identities, unresolved-local behavior, native suppression, dependency cost, and ecosystem neutrality. Produce evidence for the extraction waypoint; do not replace the delivered project-local adapter in this ticket.

## Answer

Compose the host's native lifecycle, dependency traversal, resolver ecosystem, policy matcher, and suppression mechanics. On ESLint and version-pinned ESLint-compatible hosts, prefer `eslint-plugin-boundaries` for those mechanics only after the complete Righting black-box suite passes; keep the validated direct Oxlint 1.75 adapter as dogfood evidence rather than replacing it here.

Righting must retain the thin semantic layer: normalized-contract/version validation, exact source/scope classification, contract translation, stable `righting/*` identities, fail-closed unresolved-local semantics, capability accounting, and the reusable conformance record. Filename-case plugins solve casing rather than semantic roles and should be composed only if a future normalized policy explicitly requires casing.

The [research asset](../research/guardrail-plugin-composition.md) records primary sources, the exact compose/own boundary, resolver and alpha-API risks, and the remaining extraction tests.
